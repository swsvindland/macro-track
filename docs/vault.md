# Vector Vault

Export, import, cloud backup and sync groundwork shared by Pendum Body, Lift, Macros and Hydration (`body-track`,
`lift-track`, `macro-track`, `water-track`). The canonical copy lives in `vector-design/vault`; every repo carries a
byte-identical copy of the synced files, hashed in `src/vault/manifest.json` and checked by
`node scripts/vault-kit.mjs check` (part of `pnpm lint`). **Never edit a vault file in an app repo**: change it in
`vector-design/vault`, run `gen`, and sync.

This document covers what an app developer needs: the descriptor contract, the archive format, the migration rules,
the operations and the tooling. Cloud providers, the auto-backup scheduler and incoming files (M2) and change counters
and handoff (M3) are summarised where they constrain M1 code.

## 2. The descriptor contract

The vault imports exactly two app modules, statically: `src/vault/app.ts` imports `vaultApp` from `@/vault-app`
(engine, cloud, background task, tests), and `src/vault/app-ui.ts` re-exports `useVaultRefresh` from `@/vault-app-ui`
(UI only). Static imports guarantee the descriptor exists in headless background-task runs. The full contract is
`VaultApp` in `src/vault/types.ts`.

### 2.1 Import rules for `src/vault-app.ts`

The generic tests load the real descriptor in Node, so it must be Node-loadable:

- Static imports only of: types from `@/vault/types`; the leaf vault modules (`@/vault/errors`, `@/vault/engine/db`,
  `@/vault/engine/csv`, `@/vault/engine/provenance`); `../drizzle/migrations`; `@/db/schema`; pure app modules with no
  React or native imports (for example `@/lib/translations`, water `@/lib/i18n`, `@/lib/favorites`, `@/lib/metrics`;
  lift and macro `./vault-legacy`).
- Everything that touches a native module, React or a live database handle (`@/db`, `@/lib/health`,
  `@/lib/health-schedule`, `@/lib/store`, `@/lib/rest-timer`, `@/lib/data-ownership`, `@/db/provider`, notifications)
  is imported lazily inside the function that needs it: `const { expoDb } = await import("@/db")`.
- A static import the test harness cannot resolve fails with
  `vault harness: no stub for '<specifier>' …`; add the module to `stubs` in `tests/vault-fixture.cjs` only when it is
  a lazily imported runtime module, never to paper over a static native import.
- vault-kit reads `id`, `database.name`, the `tables` names, `syncIdTables` and `excludedTables` from the source without
  running it: write them as literals in the `vaultApp` object (or as a `const` of the same file).

`src/vault-app-ui.ts` exports `function useVaultRefresh(): () => void` and may import anything. The callback it returns
runs after a restore and must bring every mounted screen up to date (body/lift: the store's `refresh`; macro: store and
nutrition refresh). Live queries (water: `announceChange` drives them) refresh what renders from them, but not state a
screen seeded once from stored values: form drafts held in `useState` keep the pre-restore values while the screen stays
mounted under `/vault/import`. Re-initialise them, for example by bumping an app-owned restore counter that those forms
use as their React `key` (water: the Settings form and the reminder editor).

Leaf modules (`errors.ts`, `incoming.ts`, `engine/db.ts`, `engine/csv.ts`, `engine/provenance.ts`,
`engine/source.ts`) never reach `src/vault/app.ts`, `src/vault/app-ui.ts`, the `src/vault/index.ts` barrel,
`@/vault-app` or `@/vault-app-ui` (`check` enforces this), so app code may import them without a cycle. App code other
than the settings screen and the root layout never imports the `@/vault` barrel: `+native-intent.tsx` imports
`@/vault/incoming`, lift and macro `data-panel.tsx` import `@/vault/engine/erase`, and (M3) `health.ts` imports
`@/vault/engine/source`.

### 2.2 `VaultApp` fields

| Field | Meaning |
|---|---|
| `id` | `"body" \| "lift" \| "macro" \| "water"`; must equal the plugin option `app`. |
| `database` | `{ name, acquire, release, announceChange? }`. `name` must equal `apps.json[id].database`. body/lift/macro: `acquire` returns the app's own `expoDb` (lazy import), `release` is a no-op. water: `acquire` opens a new connection (`useNewConnection: true, enableChangeListener: false`), runs `initializeDatabase` (which sets `busy_timeout = 5000`); `release` closes it; `announceChange` nudges `useLiveQuery` after a restore. |
| `migrations` | The default export of `drizzle/migrations.js` (`{ journal, migrations }`). |
| `tables` | The **allowlist** of exported tables, parents before children (FK order). See §2.3. |
| `media` | Media sets: `{ set, directory, table, column }`; `column` holds a file basename under `Paths.document/<directory>`. |
| `summary` | key → SQL returning one row with column `v`. Runs on the export snapshot, the scratch DB and the live DB. Must include `latest` (newest user-record timestamp, ISO string or `YYYY-MM-DD`). Values are display-only. |
| `describe(values, ctx)` | Plain function (not a hook) turning `summary` values into localised count phrases with the app's own `translate`/`interpolate`; picks the `…One` key when `ctx.plural(n) === "one"`; omits zero counts. |
| `emptySql` | SQL whose `v` is truthy when the library holds no user records (rows the app writes by itself do not count: lift's default gym, water's `counters` row and drink tombstones). Default: every `role: "data"` table is empty. This is the only emptiness test (no recovery set, no confirm, auto-backup skip, handoff offer). |
| `csv(snapshot, { language })` | Manual exports only; informational CSVs (never imported). Lazily imports the app's builders. |
| `validate(db)` | Crash guards only. Runs on the export snapshot (warnings) and the migrated scratch DB (fatal issues abort with `invalidData`). See §2.4. |
| `prepareScratch(ctx)` | SQL run on the scratch DB after FK repair and integrity checks: preference repairs and the Health provenance policy for the restore situation. |
| `swap(ctx)` | `{ before?, after? }` SQL run inside the swap transaction around the delete/insert steps, legacy restores included; `after` runs after the Health-link merge. Both may read `temp._vault_live_links` (this device's links before the delete step: `key`, `local_kind`, `local_id`, `remote_id`, `fingerprint`, `origin`, `row_exists`), which exists only when `health_links` is replaced, so a hook that reads it starts `before` with `CREATE TEMP TABLE IF NOT EXISTS _vault_live_links (…)`. water: every drink the archive lacks, tombstones included, comes back as a tombstone (an acknowledged deletion may still have its BAC estimate in Health); lift: resets the fingerprint of a restored `restored:workout` link whose workout this device rewrote since, or deleted and synced the delete (its live link to that workout is a tombstone). |
| `deviceOverrides(ctx)` | Idempotent SQL run inside the swap transaction on the live DB: turns Health sync off and scrubs device state. The vault appends the installation rules for descriptors with `health`. |
| `healthEnabledSql` | SQL whose `v` is truthy when the app's Health sync is on. |
| `health` | body/lift/macro: `{ clientPrefix, rowTables }` (local kind → table holding the row). Drives the generic Health-link merge; descriptors never write merge SQL. water: absent. |
| `legacy` | lift/macro: the v1 adapter (§4.9). |
| `hooks.pauseWhenIdle(work, ms)` | Waits up to `ms` for the app's Health sync to go idle and, in the same synchronous tick, holds it off while `work` runs. Any error while acquiring becomes `healthBusy`. |
| `hooks.beforeExport(db)` | Runs on the vault connection before a snapshot or restore (water: flush queued watch/reminder drinks). |
| `hooks.afterRestore(ctx)` | Non-React follow-up after a committed restore (re-run by crash roll-forward, so idempotent). |
| `hooks.canInterrupt(db)` | M3: false while auto-presenting the handoff sheet would interrupt the user (lift: open workout or rest timer). |
| `backgroundIntervalMinutes` | The `minimumInterval` the app's other expo-background-task registrations use (the last registration wins globally): 1440, water 15. |
| `syncIdTables` | Integer-PK tables that carry the vault-owned `sync_id` column (§6.3). Absent: none (water). |
| `excludedTables` | Tables deliberately not exported (body/macro `["counter_logs"]`). Internal tables (`__drizzle_migrations`, `sqlite_sequence`, `_vault_*`) need not be listed. |

### 2.3 Tables

```ts
interface VaultTable {
  name: string;
  mode: "replace" | "keys" | "singleton";
  role: "data" | "settings" | "provenance";
  deviceColumns?: readonly string[];
  keys?: { keyColumn: string; valueColumn: string; include: readonly string[]; provenance?: readonly string[] };
  singleton?: { idColumn: string; where: string };
}
```

- `replace`: the restore deletes every live row and inserts the archive's rows, ids kept.
- `keys`: a key/value table (`preferences` in body/lift/macro). Only keys in `include` are exported and replaced; every
  other key keeps the live value. `provenance` lists the Health bookkeeping keys among them (`installation`,
  `healthInstallations`; macro also `weightSyncEpoch`, `healthFoodSince`).
- `singleton`: one row selected by `where` (water `preferences`, `"id" = 1`), upserted column by column.
- `role`: `data` = user records, `settings` = user preferences, `provenance` = Health bookkeeping (`health_links`).
  Exported either way; M3 counters treat provenance as "needs a backup" but not as a user change.
- `deviceColumns`: never exported; on restore a singleton keeps the live value and a replace row takes the column
  `DEFAULT` (water `drinks.synced_revision`, the water preference columns for Health and reminders).

Device-only preference keys (Health toggles, timestamps, permission caches) are simply left out of `include`; the
overrides set the ones a restore must change.

### 2.4 Descriptor principles

1. Tables are an explicit allowlist. A table added by a migration is not exported until the descriptor lists it;
   `check` warns when `src/db/schema.ts` declares a table that is in neither `tables` nor `excludedTables`.
2. Validators reject only what would crash the app or break an invariant its code assumes (JSON shape it parses
   without guards, enum values it switches on). Never business bounds: anything the app tolerates is a non-fatal issue.
   FK orphans are repaired generically, not validated. Use the helpers of `@/vault/engine/db` (`countWhere`,
   `jsonObject`, `jsonArray`, `notIn`) so checks read uniformly.
3. Every override is idempotent SQL.
4. The descriptor is Node-loadable (§2.1).

## 3. Wiring a repo

Before the first sync (`sync` refuses otherwise):

1. `package.json`: the vault's dependencies installed (`fflate` `^0.8.3`, `expo-file-system` `~57.0.6`,
   `expo-sharing` `~57.0.22`, `expo-constants`, `expo-background-task`, `expo-task-manager`, `expo-sqlite`,
   `drizzle-orm`, `expo-router`; add with `pnpm add`); `scripts.lint` ends with `&& node scripts/vault-kit.mjs check`.
   `scripts.test` is unchanged: its glob picks up `tests/vault.test.*` and `tests/vault-app.test.*`.
2. `src/vault-app.ts`, `src/vault-app-ui.ts`, `tests/vault-fixture.cjs` (start from `vector-design/vault/dev/<app>/`).
3. `.prettierignore`, under `# Vector Vault: synced from vector-design/vault and hash-checked (vault-kit check).`:
   `src/vault/`, `src/app/vault/`, `modules/vector-vault/`, `plugins/with-vector-vault.js`, `scripts/vault-kit.mjs`,
   `docs/vault.md`, `tests/vault.test.*`, `tests/vault-harness.cjs`, `tests/vault/`. `.gitignore`:
   `modules/*/android/build/`, `modules/*/ios/build/`.
4. `app.json`: the plugin entry appended as the **last** element of `expo.plugins` (plugins listed earlier run their
   mods later and could override the vault's Info.plist keys; `check` fails when `expo-document-picker` or a plugin
   setting `UIFileSharingEnabled` comes before it):

   ```json
   ["./plugins/with-vector-vault", { "app": "<id>", "icloud": false, "google": { "iosClientId": null, "android": false } }]
   ```

   Options are build flags only (`icloud`, `google`, `selftest`); per-app facts come from `src/vault/apps.json`.
   Environment overrides for per-profile builds: `VECTOR_VAULT_ICLOUD`, `VECTOR_VAULT_GOOGLE_IOS_CLIENT_ID`,
   `VECTOR_VAULT_GOOGLE_ANDROID` (put them in `eas.json` `build.<profile>.env` or `.env`, never only on a local
   `expo prebuild` command line). JS reads the resolved flags from the native module, never from
   `Constants.expoConfig.extra`.

Then:

5. Settings: render `<VaultSection />` (lift/macro: in place of `<BackupPanel />`).
6. Root layout: render `<VaultRoot />` after migrations have run and **inside every provider `useVaultRefresh` reads**
   (macro: inside `<NutritionProvider>`). Importing `@/vault` there also defines the vault background task at module
   scope.
7. lift/macro `data-panel.tsx`: `const keep = await captureBeforeErase();` before `eraseLocalData()` and
   `await onLocalDataErased(keep);` after it.
8. Before adding an import to an app file, `grep -n 'load("<that file>"' tests/*`: several existing tests load app
   files through closed dependency maps, and an unmapped `@/…` specifier throws. Add a stub entry to each such map.

`src/app/vault/*` routes are reached only through `goVault(route)` in `src/vault/ui/nav.ts`, the one cast to `Href`, so
`tsc` passes whether or not the generated typed routes list them.

## 4. Archive format v2

### 4.1 Container

A standard ZIP (no ZIP64, no encryption) written with fflate's streaming `Zip`. Any unzip tool opens it after renaming
to `.zip`. Archives are never encrypted.

```
<name>.pendum<app>
├── data/<table>.ndjson     one per exported table, DEFLATE (level 6 manual, level 1 auto and pre-restore)
├── csv/<name>.csv          manual exports only, DEFLATE; informational, never imported
├── media/<set>/<name>      photos, STORED; only items with embedded: true
├── README.txt              English explanation of the format
└── manifest.json           written last (sizes and hashes of everything above)
```

Readers locate entries through the central directory, never by streaming local headers, so entry order does not
matter. Entry names: ASCII `[A-Za-z0-9._/-]`, no leading `/`, no `..` segment, no `\`, at most 200 bytes. Every
non-manifest entry must be listed in the manifest; unlisted entries are ignored.

Per-app identity (`src/vault/apps.json`): extension `pendumbody` / `pendumlift` / `pendummacros` / `pendumwater`, UTI
`dev.svindland.pendum.<app>.archive` (conforms to `public.data` and `public.content`, not `public.zip-archive`), MIME
`application/vnd.pendum.<app>+zip`. `apps.json` also holds `database`, `journal` and `mediaDirs` (for the Android backup
rules) and `syncIdBaseline` (§6).

### 4.2 File names

| Kind | Name |
|---|---|
| `manual` | `<fileStem>-<YYYY>-<MM>-<DD>-<HHmmss>.<ext>`, local time (`PendumLift-2026-10-04-153012.pendumlift`) |
| `auto` | `<app>-<yyyyMMdd>T<HHmmss>Z-auto-<rand4>.<ext>`, UTC (`body-20261004T153012Z-auto-k3f9.pendumbody`); retention prunes only names matching this grammar |
| `pre-restore` | `Documents/PendumVault/recovery/<yyyyMMdd>T<HHmmss>Z-<rand4>/data.<ext>` |

### 4.3 `manifest.json`

UTF-8 JSON. Readers ignore unknown properties. `parseManifest()` (`src/vault/engine/manifest.ts`) implements the
normative schema (spec §2.4). Required members:

| Member | Content |
|---|---|
| `format`, `formatVersion`, `minReaderVersion` | `"pendum.archive"`, `2`, `2` |
| `kind` | `manual` \| `auto` \| `pre-restore` |
| `createdAt` | ISO-8601 UTC with milliseconds |
| `app` | `id`, `bundleId`, `name`, `version`, `build`, `platform`, `osVersion`, `vault` (writer's `VAULT_VERSION`) |
| `schema` | `applied` (Drizzle journal entries applied), `lastCreatedAt` (= `journal[applied-1].when`), `lastTag`, `journalLength` |
| `device` | `id` (uuid), `platform`, `kind` (`phone`/`tablet`), `model` |
| `library` | `id` (uuid); M3 adds `gen`, `seq`, `vector`, `adoptedFrom` |
| `tables[]` | `name`, `mode`, `file`, `rows`, `columns` (exported columns in `PRAGMA table_info` order), `keys` (keys mode: the key universe), `sequence` (`sqlite_sequence.seq` or null), `sha256` and `bytes` of the uncompressed NDJSON |
| `media[]` | `set`, `name`, `bytes`, `sha256`, `embedded` |
| `files[]` | CSV and README entries: `path`, `role`, `sha256`, `bytes` |
| `counts` | the descriptor's `summary` values (preview only, never trusted) |

Optional: `missingMedia` (names rows referenced but the writer did not have), `vaultColumns` (vault-owned columns present
in the data, today `["sync_id"]`), `warnings` (export-time FK and validator findings), `provenance`
(`{ health, healthSyncOn }`).

### 4.4 NDJSON rows

One file per table, UTF-8 without BOM, one JSON object per line, every line terminated by `\n`. Keys are the column
names exactly as in the database, every exported column present on every line. Values are the **raw stored values**:
no Drizzle mapping (JSON columns stay JSON text, booleans 0/1, timestamps in whatever unit the column stores).

| SQLite storage class | JSON |
|---|---|
| NULL | `null` |
| INTEGER, \|v\| ≤ 2^53−1 | number |
| INTEGER beyond that | `{"$int":"<decimal>"}` (only accepted for INTEGER/NUMERIC affinity columns) |
| REAL, finite | number (`80.0` is written `80`; REAL affinity restores it) |
| REAL ±∞ | `{"$real":"Infinity"}` / `{"$real":"-Infinity"}` |
| TEXT | string |
| BLOB | `{"$hex":"<lowercase hex>"}` |

Any other object or an array is `corrupt`. Exported tables must be rowid tables (the exporter asserts it).

### 4.5 Media

The exporter walks rows, not directories: `SELECT DISTINCT <column> FROM <table>` per media set. Names must match
`^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. Referenced files that are absent (or badly named) go to `missingMedia`; files no
row references are never exported. `manual` archives embed files (STORED); `auto` and `pre-restore` archives list them
with `embedded: false` (cloud blobs or the recovery set's `media/`). `missingMedia` is normal: a phone restored from
Android cloud Auto Backup has photo rows without files.

### 4.6 CSV and README

CSV (manual only): UTF-8 with BOM, CRLF, every cell quoted, cells starting with `= + - @` prefixed with `'`
(`csvLine()` in `src/vault/engine/csv.ts`). `README.txt` is fixed English text explaining the layout and that the file
is not encrypted.

### 4.7 Compatibility rules (reader)

1. `format` ≠ `"pendum.archive"` → `notArchive`.
2. `minReaderVersion > READER_VERSION` → `newer`. A higher `formatVersion` with a readable `minReaderVersion` is read
   normally.
3. `app.id` ≠ the descriptor `id` → `wrongApp` (checked before the schema: body and macro share early migrations).
4. With `J` = the app's journal and `N` = `schema.applied`: `N > J.length` → `newer`; `J[N-1]` `when`/`tag` differ
   from the manifest → `unknownSchema`; otherwise replay at level `N` and migrate forward.
5. Every manifest table must be a descriptor table; every manifest column must exist at level `N`, be a vault-owned
   column this reader owns, or be listed in `vaultColumns` (a future vault-owned column: dropped). Else
   `unknownSchema`.
6. **Table presence**: a descriptor table is replaced only if the manifest lists it or it does not exist at level `N`
   (created later by a migration, so empty is its true state). A table that existed at level `N` but is missing from
   the manifest keeps its live rows (and gets no media plan).
7. Within format 2 every change is additive (new optional manifest fields, new vault-owned columns). A non-additive
   change bumps `formatVersion` and `minReaderVersion` to 3.

### 4.8 Limits (every archive is untrusted input)

Archive and entries ≤ 4 GiB; central directory ≤ 65,535 entries and ≤ 16 MiB; `manifest.json` ≤ 4 MiB; NDJSON lines
≤ 8 MiB; inflate is fed 16 KiB slices and fails `corrupt` as soon as output exceeds the manifest `bytes`; DEFLATE ratio
≤ 1100:1; every extracted file is checked against manifest `bytes` and `sha256` before use; total size is checked
against free disk space before extraction (`insufficientSpace`). Rows are inserted with bound parameters only;
identifiers come from the descriptor and are checked against `PRAGMA table_info`. No foreign SQLite file is ever
opened: restores replay rows into a database built from the app's own migrations.

### 4.9 Legacy v1 import (lift and macro)

A file that is not a ZIP and starts with `{` is parsed as JSON (cap: `legacy.maxBytes`, else `legacyTooLarge`):
`lift-track-backup` / `macro-track-backup` are parsed directly; the `…-encrypted-backup` forms ask for the password (the
only password prompt in the vault; wrong password → `legacyPasswordWrong`); another app's format → `wrongApp`. The
adapter (`src/vault-legacy.ts`) reuses the app's `decryptBackupText` and `parseBackup` and writes rows into a scratch DB
at the current schema level through Drizzle; the rest of the restore pipeline is shared. The adapter declares which
tables and preference keys it replaces (macro keeps `measurements`, `photos` and non-weight Health links), and its own
overrides: Health sync off, the live `installation` kept, `"*"` added to `healthInstallations`. `recoveryCopy(db)`
offers the old v1 pre-restore copy (resolved by basename under `LiftTrackBackups/` / `MacroTrackBackups/`) until the
next v2 restore commits.

## 5. What the vault keeps in the database and on disk

All vault objects are **runtime-owned**: created idempotently by the vault, never by Drizzle migrations, never mapped
in `schema.ts`, never exported (except `sync_id`).

| Object | Purpose |
|---|---|
| `_vault_state` (`key` TEXT PK, `value` TEXT, `WITHOUT ROWID`) | device id and fingerprint, library id, `recovery.latest`, `restore.lastOp`, cloud and handoff state, lineage |
| `sync_id` column, `_vault_sid_<t>` unique index, `_vault_sid_<t>_i` fill trigger | stable row ids on every `syncIdTables` table (§6.3) |
| `_vault_clock`, `_vault_c_<t>_i/_u/_d` triggers (M3) | change counters `gen` (anything exported changed) and `seq` (a user change) |

On disk (`Paths.document`):

| Path | Content |
|---|---|
| `PendumVault/device.json` | the device anchor `{ deviceId, createdAt }`; never backed up, never deleted by cleanup |
| `PendumVault/journal.json` | the crash journal of a running or interrupted restore |
| `PendumVault/recovery/<id>/` | a complete recovery set: `data.<ext>` (`pre-restore` archive) + `media/<set>/<name>` (displaced photos); `<id>.partial/` while incomplete |
| `PendumVault/work/<op>/` | per-operation scratch (snapshots, extracted entries, staged media) |

`PendumVault/` is excluded from iOS device backup and from the Android backup rules. Manual exports for the share sheet
are written to `Paths.cache/PendumVault/out/` and cleaned after 24 h.

**Device id** (`device.id`): created on the first start and mirrored in the anchor. A database whose device id does
not match the anchor arrived through an OS backup, device transfer or Auto Backup reinstall (a clone): the vault mints
a new device id, clears cloud state, and rotates the Health installation as for an other-device restore.
**Library id** (`library.id`): identifies a dataset lineage; a restore joins the archive's library; erase starts a
new one.

## 6. Migrations: append-only, additive, `sync_id` ownership

These rules exist because restores replay historical migrations and because the vault adds objects Drizzle does not
know about.

### 6.1 Append-only

A released `drizzle/NNNN_*.sql` file is **never edited**. A restore of an older archive builds a scratch DB by
replaying the app's own migrations up to the archive's level `N` (a truncated journal), inserts the rows, then
migrates forward with the current journal. Editing a released migration changes what level `N` means and breaks
every older archive (`unknownSchema`, or silently different data).

### 6.2 Additive

New migrations are `ALTER TABLE … ADD COLUMN`, `CREATE TABLE`, `CREATE INDEX` and data updates. Avoid drizzle-kit
**table rebuilds** (`CREATE TABLE __new_<t>` … `INSERT … SELECT` … `DROP TABLE` … `RENAME`):

- Drizzle runs all pending migrations in one transaction, where `PRAGMA foreign_keys` is a no-op. lift opens with
  `foreign_keys = ON`, so rebuilding a parent table cascade-deletes its children on every upgraded device.
- A rebuild drops the vault's `sync_id` column, index and triggers (Drizzle's snapshot does not know them). `check`
  fails a rebuild of a `syncIdTables` table in any migration after `apps.json[<id>].syncIdBaseline` (body 2, lift 4,
  macro 13, water 9; lift's released `0004` rebuild of `muscle_feedback` predates the baseline and is allowed).
  `ensureSyncIds()` would re-add and backfill the column, but that table's ids would be regenerated once.
- A rebuild resets the table's `sqlite_sequence` to `max(id)`; the restore swap never lets a sequence decrease, but app
  code must not rely on that either.

When a rebuild is truly unavoidable for a table not in `syncIdTables` (and not a lift FK parent), it is allowed by
`check`, and the G5b test shows the restore path survives it.

### 6.3 `sync_id` ownership rule

`sync_id` is owned by the vault, not by the app:

- `ensureSyncIds()` (at every start, inside the vault lock) runs for each `syncIdTables` table, skipping steps already
  done: `ALTER TABLE "t" ADD COLUMN "sync_id" TEXT`, a backfill with random v4 UUIDs, `CREATE UNIQUE INDEX
  "_vault_sid_<t>"`, and an `AFTER INSERT` trigger that fills a NULL `sync_id` for every writer on every connection.
- The column is **not mapped in `schema.ts`**. Drizzle never selects unmapped columns, so app code that copies rows
  (repeating a workout, copying a food day) cannot copy a `sync_id` and violate the unique index. Never write
  `INSERT … SELECT *` between `syncIdTables` tables.
- It is exported like any other column (appended last in `PRAGMA` order) and listed in the manifest's `vaultColumns`;
  restored rows keep their archived ids.
- Migrations must not add a `sync_id` column or create an index named `_vault_*`: on every upgraded device the column
  already exists, so `ADD COLUMN sync_id` fails with "duplicate column name" inside Drizzle's migration transaction and
  the app never starts (fresh installs and tests pass, because migrations run before the vault). `check` fails such a
  migration after the baseline.
- **Taking ownership later** (real sync will likely map `sync_id` in `schema.ts`): add the mapping, let drizzle-kit
  generate the migration, then hand-edit that migration so its `ADD sync_id` statement becomes a no-op (`SELECT 1;`).
  Fresh installs still get the column from `ensureSyncIds()`.
- Text-keyed tables keep their key as the stable id and are not in `syncIdTables` (`custom_exercises.id`,
  `custom_foods.id`, `recipes.id`, `diary_days.day`, `preferences.key`, …). water has none (`drinks.id` is a UUID).

### 6.4 Dropping a column of an exported table

From M3, the vault's change-counter triggers name every counted column, and SQLite refuses `ALTER TABLE … DROP COLUMN`
while a trigger references the column. The migration would fail on every upgraded device (never on fresh installs or
in tests). Hand-edit the generated migration so it first drops the table's three triggers, each followed by drizzle's
breakpoint:

```sql
DROP TRIGGER IF EXISTS "_vault_c_<t>_i";
--> statement-breakpoint
DROP TRIGGER IF EXISTS "_vault_c_<t>_u";
--> statement-breakpoint
DROP TRIGGER IF EXISTS "_vault_c_<t>_d";
--> statement-breakpoint
ALTER TABLE `<t>` DROP COLUMN `<column>`;
```

The drops are no-ops before M3; the next start recreates the triggers for the new column set. `check` fails a
post-baseline `DROP COLUMN` on a descriptor table without them. `RENAME COLUMN` needs nothing.

## 7. Adding a table, a column or a preference key

**A new table**

1. Write an additive migration (§6) with drizzle-kit; never edit a released one.
2. Decide whether it is user data. If yes, add it to `tables` in FK order (parents first) with `mode` and `role`;
   list device-local columns in `deviceColumns`. If not, add it to `excludedTables` (otherwise `check` warns).
3. Integer primary key holding user records → add it to `syncIdTables`. No migration: the column appears at the next
   start.
4. If its rows reference files, add a `media` set; if Health links point at it, add it to `health.rowTables`.
5. Add `validate` checks only for shapes the app parses without guards; extend `summary`, `describe` and `csv` if the
   preview or CSV should show it; extend `emptySql` if the app writes rows into it by itself.
6. Seed it in `tests/vault-fixture.cjs` and run the vault tests (§12).

Older archives restore correctly without edits: an archive written before the table existed replaces it with an
empty table (§4.7 rule 6); one written by an app version whose descriptor did not list it yet keeps the live rows.

**A new column**: an additive `ADD COLUMN` (with a `DEFAULT` when it is `NOT NULL`). It is exported automatically;
add it to `deviceColumns` if it is device state. Restores of older archives get the migrated or default value from
the forward migration.

**A new preference key** (keys-mode tables): add it to `include` if it is a user setting that should travel; also to
`provenance` if it is Health bookkeeping. Leave device state (sync toggles, timestamps, caches) out. Archives written
before the key existed keep this device's value.

**Removing a column**: §6.4. **Removing a table**: drop it from `tables` (or move it to `excludedTables`) in the same
change as the migration.

## 8. Operations: start, export, open, restore, recovery

UI code calls only the lock-taking entry points in `src/vault/ops.ts`. Each takes the process-wide vault lock and runs
`ensureReady(db)` first: crash-journal recovery, exclude `PendumVault/` from iOS backup, device and library ids, sync
ids (M3: the clock). So no manifest is ever written without a device and library id.

| Entry point | Lock | Does |
|---|---|---|
| `startVault()` | `recover`, waits | called once by `<VaultRoot />` after migrations; returns at once when the native module is missing (Expo Go, web) |
| `runExport()` | `export`, waits | `exportArchive` |
| `runOpen()` | `inspect`, waits | `openArchive` → preview |
| `runRestore()` | `restore`, waits | `restoreArchive` |

The lock serialises every vault operation in the process (UI and background tasks share the JS runtime); the
automatic backup takes it without waiting and skips its run when it is held.

### 8.1 Export

1. `hooks.beforeExport`, then a consistent snapshot with `VACUUM INTO` (one synchronous statement; the device id,
   library id and counters are read from the same copy).
2. Per descriptor table: NDJSON written from the snapshot in pages of 500 rows, hashed natively.
3. Media listed from the rows and hashed; missing files recorded.
4. Export-time validation: `PRAGMA foreign_key_check` and `validate` findings become manifest `warnings`; the export
   still succeeds (the UI shows a warning).
5. CSV (manual), then the ZIP: data, CSV, media, README, manifest last.

### 8.2 Open

The file is copied into `work/<op>/in/`, the central directory and manifest are read and checked (§4.7), and a preview
is built: incoming counts, current counts, older schema, cross-platform, same device, whether the live library is
empty, whether there are newer local changes, media totals. No database is touched.

### 8.3 Restore

Health sync is paused for the whole restore (`hooks.pauseWhenIdle`, ≤ 120 s, else `healthBusy`).

1. Disk check; extract and verify every data entry (size and sha256).
2. **Scratch DB**: replay the app's migrations to the archive's level `N`, add vault-owned columns, insert the rows,
   restore `sqlite_sequence`, migrate forward, backfill sync ids, repair FK orphans by their `ON DELETE` action
   (CASCADE deletes, SET NULL nulls; NO ACTION/RESTRICT → `invalidData`), `integrity_check`, `prepareScratch`, `validate`.
3. **Media plan**: for each photo the restored rows reference: keep identical live files, stage verified copies of
   archive files, keep a live file the archive lacks, skip what nobody has. A live file is never moved away while a
   restored row references its name unless a verified replacement is staged.
4. Last cancellation point.
5. **Commit section**, one synchronous block on the live connection: write the journal; `VACUUM INTO` the recovery
   snapshot (skipped when the live library is empty); move displaced photos into the recovery set and staged photos
   into place; then one transaction (`BEGIN IMMEDIATE`, with `foreign_keys` off and `synchronous = FULL` for it):
   delete and insert the replaced tables with explicit column lists, merge Health links, raise sequences (never
   lowered), apply overrides, write every vault state change, `foreign_key_check`, `COMMIT`. On water, a write by
   another connection between the snapshot and the transaction is detected (`PRAGMA data_version`) and the block is
   retried, up to 3 times, then `busy`.
6. After commit: package the recovery set (`pre-restore` archive), keep the newest 2 sets, `announceChange`,
   `afterRestore`, clear the journal. A failure here is reported as `afterRestoreFailed`, never as "nothing was
   changed". The UI then calls the `useVaultRefresh` callback.

Every restore turns Health sync off; the user re-enables it with the app's existing toggle. The Health links travel
with the rows and are merged with this device's links, so re-enabling upserts the same samples under their existing
client ids instead of duplicating them. A key both sides know takes this device's state of its sample: a link this
device has since turned into a tombstone (`fingerprint = 'deleted'`) makes the archive's link one too, so the next sync
writes that record again. A link of this device that the archive lacks, tombstones included, is kept as it is when the
archive links nothing at that record's id, and parked at local id -1 when it links something there under another key
(another installation's export or a Health import: the restored row is then another record), so the next sync removes
this device's sample instead of leaving it in Health. Tombstones are carried so that a later restore of a file that
still links a deleted sample rewrites it instead of trusting a sample that is gone: an archive link whose remote id a
local tombstone holds loses its fingerprint (lift's `restored:workout` links reach their sample by that id only). A
link parked at -1 under the installation the restore keeps (same device, v1 file) whose key names an id that no link
holds (`…:<kind>:<id>`) takes that id: the next sync writes a restored record without a link under that very key, and
the apps' export loops do not move a link's local id.

The installation the vault leaves (spec §5.2): a same-device restore keeps the archive's `installation`, or the live one
when the archive has none; another device's or platform's archive (or a handoff) mints a fresh one, which names only
records created from now on (restored records keep their link keys); a v1 file keeps the live one. `healthInstallations` becomes the union of both
sides' lists and installations, plus `"*"` (no sample this app wrote under any installation is imported as an outside
reading) for a v1 file and, since 1.0.3, for another device's archive that names no installation: it was made before
that device first synced with Health, so whatever installation it synced under afterwards is in no list, and its
samples may be in this device's store (a second iPhone of the same Apple Account, the same phone after a reinstall).
The restored records of such an archive have no links, so on a shared store the next sync writes each once more next
to the source's sample (a known limitation, spec §5.9).

### 8.4 Recovery sets and the crash journal

A recovery set (`PendumVault/recovery/<id>/`) is taken before every restore over a non-empty library. Settings offers
"Restore data from before {date}" for the newest complete set; restoring it creates a new set first, so undo can be
undone. `.partial` sets are never offered.

`recoverJournal()` runs at the start of `ensureReady`, under the lock, and never touches an operation still running in
this process. If the swap committed (`_vault_state['restore.lastOp']` equals the journal's op) it rolls forward
(pending media moves, recovery packaging, `announceChange`, `afterRestore`); otherwise it rolls back the media moves
and deletes the partial set. While a committed restore's recovery set cannot be packaged (disk full), new restores fail
with `insufficientSpace` so the pending set is never overwritten.

### 8.5 Erase (lift and macro)

`captureBeforeErase()` keeps the Health lineage (`healthInstallations` + `installation`) so erased data is not
re-imported from Health; `onLocalDataErased(token)` deletes recovery sets and work files (never `device.json`), starts a
new library id, turns cloud backup off and writes the lineage back. Neither needs the native module: without it (Expo
Go, a build from before the vault's prebuild) nothing fails after the app's erase; `library.id` is removed instead of
replaced and the next start with the module mints the new one.

## 9. Errors and cancellation

`src/vault/errors.ts` (a leaf): `VaultError(code, info)`, `toVaultError(e, fallback)`, `VAULT_ERROR_CODES`,
`checkAborted(signal)`. Library code never throws user-visible English; the UI renders a code with
`errorText(v, code, trigger)` from `src/vault/ui/labels.ts`. `cancelled` renders nothing.

| Code | Meaning |
|---|---|
| `notArchive`, `wrongApp`, `newer`, `unknownSchema`, `corrupt` | the file (§4.7, §4.8) |
| `invalidData` | a fatal validator issue, an FK orphan that cannot be repaired, or a constraint failure |
| `migrationPending` | the live DB has unapplied migrations (should not happen after `<VaultRoot />` mounts) |
| `busy`, `healthBusy` | another vault operation, another connection's writes, or a Health sync that did not go idle |
| `insufficientSpace` | not enough free space, or an unfinished committed restore |
| `exportFailed`, `restoreFailed` | anything else, before the commit |
| `legacyPasswordRequired`, `legacyPasswordWrong`, `legacyTooLarge` | v1 files |
| `cancelled`, `unsupported`, `shareUnavailable` | user cancel, no native module, no share target |

Cloud codes (`icloud*`, `google*`, `network`, `provider`, `peerNotReady`) arrive with M2/M3.

**Cancellation**: the only checkpoint is `checkAborted(signal)`, which reads `signal.aborted`. React Native's
`AbortSignal` (`abort-controller@3`) has nothing else, so vault code never uses the Node-only `AbortSignal` members
(`check` fails on them in `src/vault/` and `src/app/vault/`, comments included). The test harness replaces Node's
`AbortController` with a device-shaped one. A restore honours `signal` only until the commit section starts.

## 10. Versions

`src/vault/version.ts`:

- `VAULT_VERSION`: the package version (manifest `version`, every archive's `app.vault`). Changed by `vault-kit bump`.
- `FORMAT_VERSION = 2`, `MIN_READER_VERSION = 2`, `READER_VERSION = 2`: the archive format. Changed only by a deliberate
  format change with a `CHANGELOG.md` entry, never by `bump`.

`src/vault/types.ts` is the contract. After the scaffold it is append-only: new members carry a `// added by <task>`
comment and a `CHANGELOG.md` line; existing members are never changed or removed without revisiting the contract.

The vault requires kit `>=1.3.1` (`check` reads `src/vector/manifest.json`). Vault UI imports only from `@/vector`
and has zero kit-lint hits; `vector.allow.json` must never list a vault path.

## 11. Tooling: vault-kit

`node scripts/vault-kit.mjs <command>`. Plain Node ESM, no dependencies.

| Command | Where | Does |
|---|---|---|
| `gen` | canonical | Hashes every vault file into `src/vault/manifest.json` (with the version, format, `requires.vector` and the required dependencies). Run after every edit. |
| `bump <patch\|minor\|major>` | canonical | Bumps `VAULT_VERSION` and `modules/vector-vault/package.json`, prepends a `CHANGELOG.md` stub, runs `gen`. |
| `sync <repo…> [--force]` | canonical | Copies changed files byte-for-byte into each repo, picks the test-entry variant, deletes files an earlier sync shipped that the canonical no longer has, writes the manifest. Refuses: a stale canonical manifest (run `gen`); a repo without its prerequisites (§3); locally modified vault files; a differing app file at a vault path. `--force` overrides the last three (meant for throwaway copies). Never touches files outside the vault paths. |
| `check` | everywhere | Fails on: version mismatch; `modified`, `missing`, `unknown` files; an incomplete `apps.json` row; kit version; a vault path in `vector.allow.json`; the leaf closure; Node-only `AbortSignal` members; an `appDelegateSubscribers` name with no Swift class. In repos also: wiring (§3, descriptor `id`/`database.name` against `apps.json` and the plugin option) and the migration guards (§6). Warns on missing ignore lines and schema tables the descriptor does not mention. |
| `check --drift` | everywhere | Version and hashes only. |
| `siblings` | everywhere | Version and hash matrix across the canonical vault and the four repos; exit 1 on a mismatch. |
| `try <repo-dir> [--keep] [--only types\|lint\|tests]` | canonical | Copies the repo's tracked and untracked files (no native folders, build products, store artwork or `.expo/`) to `$VAULT_SCRATCH` or the OS temp folder, installs `node_modules` offline, syncs the canonical vault in, adds the missing wiring and the `dev/<app>/` drafts when the repo has none, then runs `tsc --noEmit`, eslint over the vault paths, both checks and the vault tests. Never writes to the repo; deletes the copy unless `--keep`. Needs git, rsync and pnpm. |

Changing the vault:

```sh
cd vector-design/vault
node scripts/vault-kit.mjs gen
node scripts/vault-kit.mjs check
node scripts/vault-kit.mjs try ../../lift-track      # FK-ON shared connection
node scripts/vault-kit.mjs try ../../water-track     # dedicated connection
node scripts/vault-kit.mjs bump patch                # when releasing; fill in CHANGELOG.md
```

A repo is synced only by its own unit of work, after its prerequisites exist:

```sh
node scripts/vault-kit.mjs gen && node scripts/vault-kit.mjs sync ../../lift-track
cd ../../lift-track && pnpm typecheck && pnpm lint && pnpm test
```

## 12. Tests

- `tests/vault.test.*` (the entry) requires every `tests/vault/<area>.cjs`: `tooling`, `engine-io`, `engine-export`,
  `engine-restore`, `engine-legacy`, `strings`, `ui-flow`, later `cloud`, `scheduler`, `groundwork`, `handoff`. They
  run in every repo against the repo's real descriptor through the repos' normal `pnpm test`.
- `tests/vault-harness.cjs` transpiles the TypeScript with the repo's `typescript` and runs it on Node shims:
  `expo-sqlite` over `node:sqlite` (opened with foreign keys off, like the device), `expo-file-system` over `node:fs`,
  the native module over `node:crypto`. Unresolvable imports throw. Requires Node ≥ 22.16; older Node skips every vault
  test with a message.
- `tests/vault-fixture.cjs` (app-owned): `{ seed(db, { level }), fresh?(db), levels, stubs }`. `seed` writes a
  representative dataset at a schema level; `fresh` writes what the app writes by itself on a fresh install (lift: the
  default gym); `levels` lists historical schema levels the restore tests replay; `stubs` maps the modules the
  descriptor imports lazily to Node fakes.
- `tests/vault-app.test.*` (app-owned): Health regressions, legacy import, validators.
- A test that expects an entry point to fail captures the one-line `[vault] <code>` diagnostic it reports (ops.ts) and
  asserts the diagnostics exactly (`engine-legacy`, `ui-flow`), so `pnpm test` prints none and an unexpected warning
  fails the test.
- On a device, the self-test (Settings row in `__DEV__` builds or with the plugin option `selftest: true`) runs the
  round-trip, atomicity, crash and FK tests against a copy of the live DB with the real native modules.

## 13. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `check`: `modified` / `missing` / `unknown` in a repo | A vault file was edited, removed or added locally. Make the change in `vector-design/vault`, `gen`, `sync`. |
| `check` in the canonical folder fails with drift | `gen` was not run after editing. |
| `sync` refuses a repo | Prerequisites missing (dependency not in `dependencies` or not installed, descriptor files, fixture, plugin entry), local edits to vault files, or an app file at a vault path. Fix the cause; `--force` only on throwaway copies after review. |
| `check`: `wiring` failures | The descriptor's `id` or `database.name` is not a literal or disagrees with `apps.json` / the plugin option; `lint` lacks the vault step; a required dependency is missing; the plugin entry is missing or listed before `expo-document-picker` / a `UIFileSharingEnabled` plugin. |
| `check`: `migration` failures | A post-baseline migration rebuilds a `syncIdTables` table, adds `sync_id`, creates a `_vault_*` index, or drops a column without the three `DROP TRIGGER IF EXISTS` lines (§6). Rewrite it additively before it ships. |
| `check`: leaf closure | A leaf module (`errors`, `incoming`, `engine/db`, `csv`, `provenance`, `source`) now reaches `app.ts`, `app-ui.ts`, the barrel or `@/vault-app*`. Move the import out of the leaf. |
| `check`: runtime-API guard | Vault code names a Node-only `AbortSignal` member. Use `checkAborted(signal)`. |
| Warning: schema declares a table in neither list | Add it to the descriptor's `tables` or `excludedTables` (§7). |
| `vault harness: no stub for '…'` | The descriptor statically imports a native/React module (make it a lazy `await import`), or a lazily imported module needs an entry in the fixture's `stubs`. |
| Vault tests skipped: "vault tests need Node ≥ 22.16" | Upgrade Node. |
| `tsc` rejects a `"/vault…"` href | Navigate with `goVault()` from `src/vault/ui/nav.ts`. |
| `try` warns "not resolvable in the copy" | `pnpm install --offline` failed, `try` cloned the repo's own `node_modules`, and that lacks a vault dependency. Add it to the repo (`pnpm add`, the T1.0 step) and retry. |
| App does not start after a migration on upgraded devices: "duplicate column name: sync_id" | A migration adds `sync_id` (§6.3). Replace that statement with `SELECT 1;` in an unreleased migration; never edit a released one. |
| …: "error in trigger … after drop column" | A `DROP COLUMN` without the trigger drops (§6.4). |
| Restore fails `unknownSchema` | The archive comes from a different migration lineage, lists a table or column this app does not know, or a released migration was edited. |
| Restore fails `newer` | The archive was written by a newer app version or format. Update the app. |
| Restore fails `invalidData` | A fatal validator issue or an unrepairable FK orphan in the archive; the export that wrote it showed a warning. The detail names the table. |
| Restore fails `healthBusy` / `busy` | A Health sync did not go idle within 120 s, or another vault operation or writer held the database. Retry. |
| Restore fails `insufficientSpace` although space was freed | A committed restore's recovery set is still unpackaged; the next start retries it. |
| Photos missing after a restore (`mediaSkipped`) | The archive listed them in `missingMedia` (the writing device lacked the files, e.g. after an Android cloud Auto Backup restore) and this device has no copy. Rows are kept. |
| Health stopped syncing after a restore | Expected: every restore turns Health sync off. Re-enable it in Settings; samples are upserted, not duplicated. |
| "Restore data from before …" missing | No restore has happened, the live library was empty at restore time (no set is taken), or the set is still `.partial`. |
